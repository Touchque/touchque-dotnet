## [5.5.0] — 2026-11-17

### Added
- **Touchque Login, moving your customers in from your own user database:** `Identity.GetUserStoreAsync()`, `SetUserStoreAsync(string? url = null, bool? enabled = null)`, `TestUserStoreAsync(string? url = null)` and `RemoveUserStoreAsync()` (GET, PUT, POST `/test` and DELETE on `/identity/user-store`; answers are the API's JSON). While a customer has no account here yet, Touchque asks your endpoint; a password it confirms is kept by Touchque (Argon2id) and that customer is not asked about again.
  - `GetUserStoreAsync` answers `url`, `enabled`, `active` (asked only while it is enabled and passwords are on), `movedIn`, `lastCall` ({ at, event, ok, status, ms, error } or null), `paused` (5 failed calls in a row pause it for a minute), `updatedAt` and `signing`; `SetUserStoreAsync` answers the same.
  - `SetUserStoreAsync` sends only the arguments that are not null: without `url` the endpoint set stays, without `enabled` it stays as it is (on for a new one). Refused with 409 `passwords_off` when it would be on while passwords are off, and 400 `invalid_request` (`field` url) for an address that is not a full https URL, carries a user name or password, is local (`localhost`, `127.0.0.1`, `[::1]`, a `.localhost` or `.test` name), is over 500 characters, or is missing with none set.
  - `TestUserStoreAsync` sends one signed `user_store.ping` to `url` (null or `""`: the endpoint set, sent as `{}`) and answers { ok, error, ms }: a failed ping is an answer, not an exception, and never pauses the endpoint.
  - `RemoveUserStoreAsync` answers an empty object (204), also when none is set; 404 `not_enabled` means Touchque Login is not set up. Accounts already moved in stay.
  - Your endpoint gets POSTs signed like Touchque's webhooks (your API secret, `x-signature`), each with `tenant`, `timestamp` and `jti`: `user_store.verify_password` { email, password } at a password sign-in of an address with no account here yet, `user_store.get_user` { email } at a password reset, an email code or a sign-up with such an address, and `user_store.ping`. `MapTouchqueWebhook` and `tq.Webhook.VerifyAsync` check them. Answer 200 `{ user: { id, email, emailVerified, name, givenName, familyName, nickname, picture, locale, phone, userMetadata, appMetadata } }` (`id` and `email`, the address asked about, required) or `{ user: null }` (404 counts as null) within 5 seconds, the same for an unknown address and a wrong password. Another status, a redirect, a body that is not JSON or no answer in 5 seconds counts as unavailable: a password sign-in is then not refused as a wrong password.
- **Touchque Login without passwords:** `UpdateTenantAsync(new { signInMethods = new { password = false, passkey = true, emailCode = true } })`. Customers sign in with a passkey or an email code and sign up with the email code; without the email code it is refused with 400 `invalid_request`, and while moving users in is on with 409 `user_store_on`. A `signInMethods` without `password` leaves passwords as they are.
- **Touchque Login passkey domain:** `Identity.SetPasskeyDomainAsync(string? domain)` (PUT `/identity/tenant` { passkeyDomain }) sets the domain customer passkeys are made for, their relying party ID: null or `""` for none (a passkey belongs to the host it was made on), one of your verified custom domains, or a domain above one of them that your organization verified (Organization → Domains: `acme.com` for `login.acme.com`), so passkeys keep working when sign-in moves to another host under it. It answers the tenant (`passkeyDomain`). Refused with 409 `passkeys_exist` when customer passkeys would be left behind (their number in `Body["count"]`: set it before customers make passkeys), 409 `not_your_domain`, 409 `organization_unavailable` (your organization's domains could not be read: try again) and 400 `invalid_request` (`field` passkeyDomain) for a value that is not a domain; before Touchque Login is set up for the workspace, 400 `invalid_request` with `field` slug.
- **Custom domains:** `Identity.CustomDomains` is an `IdentityCustomDomains`; `ListAsync()` answers the domains, as before.
  - `OverviewAsync()` answers the list as the API does, typed: `CustomDomainsOverview` with `Domains` (what `ListAsync()` returns), `VerifiedDomains` (your organization's verified domains, Organization → Domains: a passkey domain above a custom domain must be one of them; null when they could not be read) and `SlugPasskeys` (customer passkeys made on {slug}.login.touchque.com, which belong to that name and do not work on a custom domain). `Identity.GetCustomDomainsAsync()` is an alias of it.
  - `GetAsync(id)` finds the domain in the list (the API has no read by id) and, when it is not there, throws `TouchqueApiException` shaped like the API's 404: `Status` 404, `Error` `not_found`.
  - `VerifyAsync(id)` (POST `/identity/custom-domains/{id}/verify` with `{}`, the id path-encoded) checks the domain's TXT record now (a domain on one your organization verified needs none) and its DNS, and answers the domain.
- Custom-domain answers (the items of `CustomDomains.ListAsync()`, and what `CreateAsync`, `VerifyAsync`, `UpdateAsync` and `CheckDomainCertificateAsync` answer) carry `dns`, what the domain's DNS said at the last check or null (`points`: here, elsewhere or nowhere; `cloudflareProxy`, `caaBlocks`, `problems`: `dns_missing`, `points_elsewhere`, `cloudflare_proxy`, `caa_blocks`), and `autoCheckUntil`: a new domain is checked by itself every 5 minutes for 72 hours.
- README, Touchque Login: "Custom domains", "Passkey domain" and "Moving customers in from your own user database", and that Management API refusals are `TouchqueApiException` with the API's code in `Error` (its `error` field) and the field in `Body["field"]`. The snippets are compiled with the tests, and the user store endpoint is run against requests signed as Touchque signs them.

### Changed
- `Identity.CustomDomains` is an `IdentityCustomDomains`, a subclass of `IdentityCrud` (what it was), and `IdentityCrud.GetAsync` is virtual. Code that uses it compiles as before; a library built against 5.4.0 that uses `CustomDomains` needs a rebuild.

### Fixed
- **Webhooks and user store requests with an unpaired surrogate** (`Webhook.Verify`, `VerifyAsync`, `MapTouchqueWebhook`). JSON.stringify writes a lone UTF-16 surrogate as an escape (`\ud800`), e.g. in a password or email a user store is asked about. The signature check matched Touchque's (it is made over the body as received), but reading that string from the payload threw `InvalidOperationException` (a 500 from a `MapTouchqueWebhook` handler). The payload now has U+FFFD for each unpaired surrogate, so every string reads and encodes as UTF-8; a body changed after signing still fails. A body string with a lone surrogate written raw (no UTF-8 body carries one) is refused as invalid JSON instead of throwing `ArgumentException`. The tests run the shared vectors (fixtures/user-store-vectors.json).
- `CustomDomains.GetAsync(id)` sent GET `/identity/custom-domains/{id}`, which the API does not have; it now finds the domain in the list.

## [5.4.0] — 2026-11-16

### Added
- **2FA setup context: the phone shows where a first-time QR was asked for.** `Auth.GenerateSecretAsync(externalUsername, clientIp, userAgent)` and `Auth.ResetSecretAsync(externalUsername, clientIp, userAgent)` send the end user's IP and User-Agent (`clientIp`, `userAgent`, both optional) with the same rule as a login request: each only when not null or empty, as given (no trimming, no length cap). Touchque records where a QR was asked for from the request that asked for it, never in the QR, and the phone shows it before it links. The `(externalUsername, ct)` overloads stay and send the user only.
  - The adapters send them for you, the same ones their login requests carry: the guard's first-time QR and its renewal (`RequireTouchque`, `[RequireTouchque]`, `Guard.RunAsync`, `tq.StartAsync` with `StartOptions.Ip` / `UserAgent`) and the relay's `POST /enroll/start`, with its reset after a 409 (`MapTouchqueRelay`, `RelayHandler`). In ASP.NET Core the IP is `TouchqueClientIp()` as for a login: `Connection.RemoteIpAddress`, behind `UseForwardedHeaders` with your proxy as a known proxy the address it saw, never the leftmost `X-Forwarded-For`; no address, none sent.
  - `ValidateSecretResult.SetupContext` (`SetupContext`: `Ip`, `Location`, `Device`, `RequestedAt` (ISO 8601, kept as a string), `FarFromPhone`), with `SetupLocation` (`City`, `Country`, `CountryCode`) and `SetupDevice` (`Browser`, `Os`, `Model`). Every field is nullable; the context is null when the answer has none (an older QR, an API before this change). Read leniently: a field that is missing, null or of another type is null, never an error; unknown fields are kept in `Extra`.
  - README: "Linking the phone (first-time QR)"; its snippet is compiled with the tests.

### Changed
- Docs: `DeviceRiskSignal.Code` lists the codes the API now returns too: `device_pointer_synthetic`, `device_new_storage_burst` and `device_network_signup_burst` (phones are told apart only by their stored id and key since 2026-11-15, so the risk engine counts new browsers and sign-ups per kind of phone and network). No code change.

## [5.3.0] — 2026-11-15

### Added
- **Cross App Access (ID-JAG) sender-constrained with DPoP (RFC 9449).** `CrossAppAccess.CreateIdJagDpopKey()` makes a P-256 key (`IdJagDpopKey`, disposable). Set it as `DpopKey` on `RequestIdJagOptions` (the proof goes to the identity provider, which binds the ID-JAG to it with `cnf.jkt`; `IdJagGrant.DpopBound` says whether the returned ID-JAG carries that key's thumbprint) and on `RedeemIdJagOptions` (a fresh proof for the authorization server's token endpoint). `IdJagVerifier.VerifyAsync(assertion, clientId, dpopJkt)` refuses a bound ID-JAG without a matching proof thumbprint, before its jti is used up, and sets `IdJagClaims.CnfJkt`; the two-argument overload refuses bound ID-JAGs and verifies unbound ones as before.
  - `CrossAppAccess.IdJagDpopProof(key, url, method = "POST", accessToken = null, nonce = null)`: a proof for one request; the two-argument call is a token endpoint's POST. For a call with the DPoP-bound access token, give its method and the token (`ath`, the base64url SHA-256 of its ASCII bytes), and send `Authorization: DPoP <token>` with `DPoP: <proof>`. `nonce` adds a server's nonce. The header's `jwk` is the key's public part only: `kty`, `crv`, `x`, `y`.
    - `htm` is the method without leading and trailing ASCII whitespace (space, tab, CR, LF, VT, FF; not NUL, and not the Unicode whitespace `string.Trim()` takes, such as U+00A0), `POST` when that leaves nothing, uppercased; a method with anything but RFC 9110 token characters throws `TouchqueConfigException`. A null or empty `accessToken` or `nonce` is left out; a `nonce` you pass goes in as given, unchecked.
    - `htu` is the URL as System.Uri parses it, so System.Uri must accept it as an absolute http or https URL (else `TouchqueConfigException`): the scheme and host lowercased (punycode for an IDN host), user info and the default port dropped, `/` for an empty path, no query or fragment. The path is kept as given, percent-escapes included, except that `\` counts as `/`, `.` and `..` segments are resolved, and a character a path cannot hold as it is (a space, a control or non-ASCII character, `"`, `<`, `>`, `^`, a backtick, `{`, `}`) is percent-encoded as UTF-8. This is not a full WHATWG URL normalization: a host System.Uri reads differently (such as `[::ffff:1.2.3.4]`) is written its way.
    - HttpClient sends a URL in System.Uri's form (`%7E` as `~`, `|` as `%7C`): the token endpoint proofs name the URL that way, and a resource call's proof is made from the URI the request sends (`request.RequestUri.AbsoluteUri`).
  - Server nonces (RFC 9449 section 8): with a `DpopKey`, `RequestIdJagAsync` and `RedeemIdJagAsync` send the same request once more (the same form body and client authentication) with a new proof that carries the nonce, when the token endpoint answers 400 or 401 `use_dpop_nonce` (in the JSON body, or for a 401 in `WWW-Authenticate: DPoP error="use_dpop_nonce"`) with a valid `DPoP-Nonce` header: RFC 9449 nonce syntax (one or more printable ASCII characters except space, `"` and `\`), the same value each time if the header repeats. A missing, empty, invalid or conflicting `DPoP-Nonce` gets no retry. Once per call: a second refusal throws as usual. Without a key nothing changes (no `DPoP` header, no retry).
    - `TouchqueIdJagException.DpopNonce`, for a retry by hand: the latest valid `DPoP-Nonce` the server sent during the call, in any answer, a 2xx too (the retry answer's when it had one, else the first answer's), never an invalid value. Every error the two calls throw carries it, `invalid_response` and `temporarily_unavailable` included.
    - `WWW-Authenticate` only decides this retry: it never sets `Error`, which comes from the JSON body (see Changed).
    - `WWW-Authenticate` is read in one pass, linear in its length, that never throws. Only a DPoP challenge's own `error` parameter counts, and only when it is exactly `use_dpop_nonce` (scheme and parameter names in any case). A value is a token or a quoted-string: a comma or an `error=` inside quotes is part of it, a quoted-pair (`\` and a character) is that character, and a quoted-string without its closing quote has no value. With the 256 KB header limit (see Changed), a 64 KB `WWW-Authenticate` still gives the answer or a `TouchqueIdJagException` in milliseconds.
  - An authorization server of another company that accepts Touchque ID-JAGs must verify the DPoP proof itself (`typ`, the signature with the `jwk` in it, `htm`, `htu`, `iat`, each `jti` once) and check `cnf.jkt`, refusing a bound ID-JAG unless the proof key's thumbprint matches it; this SDK's verifier does the `cnf.jkt` part when given the proof key's thumbprint. Such a server verifies the proof, and any nonce it requires, before it calls the verifier, which uses up the ID-JAG's `jti`.

### Changed
- **`RequestIdJagAsync` and `RedeemIdJagAsync`: a token endpoint that cannot be reached or read throws `TouchqueIdJagException` `temporarily_unavailable`**, on the first request or on the nonce retry, instead of 5.2.0's `HttpRequestException` or `TaskCanceledException`: refused, reset, DNS, no answer within the 10 s timeout, or an answer HttpClient refuses (a status or header line it cannot parse, a body shorter than its `Content-Length`, a bad chunk). Its `Status` is null and `InnerException` is HttpClient's exception (a new constructor, `TouchqueIdJagException(error, message, status, innerException)`, takes it). They now read up to 256 KB of response headers (64 KB before, SocketsHttpHandler's default); an answer with more is `temporarily_unavailable` too. A cancellation you ask for with the `CancellationToken` still throws `OperationCanceledException`. Reading the issuer's OpenID configuration (discovery) is unchanged.
- **`RequestIdJagAsync` and `RedeemIdJagAsync`: only a 2xx answer is a success.** 5.2.0 read a 3xx answer (redirects are not followed) as one; now it throws `TouchqueIdJagException` with that `Status`, like a 4xx or 5xx. A 2xx answer that is not a JSON object (not JSON, empty, `null`, an array, a string, a number) gave `RedeemIdJagAsync` an empty object and `RequestIdJagAsync` an `invalid_response` without a `Status`; both now throw `invalid_response` with the 2xx `Status`. `Error` is the answer's JSON `error` only when it is an RFC 6749 error code (printable ASCII or space, no `"` or `\`) of at most 128 characters, else `server_error`; 5.2.0 took any string.
- README, "Cross App Access (ID-JAG) and A2A agent cards": what `RequestIdJagAsync` and `RedeemIdJagAsync` throw (`temporarily_unavailable`, `invalid_response`, a refusal's `Status` and `Error`); DPoP binding (`DpopKey`, `DpopBound`), the one nonce retry for a valid nonce and `DpopNonce`, a call with the DPoP-bound access token (`Authorization: DPoP`, a proof made from the URI and method the request sends: `call.RequestUri!.AbsoluteUri`, `call.Method.Method`), the `htu` and `htm` rules, what another company's authorization server must check itself (the proof and any nonce before calling the verifier, which uses up the `jti`) and the `cnf.jkt` part `VerifyAsync(assertion, clientId, dpopJkt)` does. The verifier is built once: its used-once jti store and key cache live in the instance. The snippets are compiled with the tests.
- README, "Guard inside your handler": in tests, `RequireTouchque()`, `[RequireTouchque]`, `MapTouchqueWebhook` and the handler take the `TouchqueClient` that `AddTouchque` registers from `RequestServices` on each request, and `MapTouchqueRelay` takes it once when it maps its routes, never the client of `Guard.SetDefaultClient`. Replace that registration with `ConfigureTestServices` (`AddSingleton`, not `TryAddSingleton`), or give the registered client test keys in `Configure<TouchqueOptions>` with a fake API as `BaseUrl` or a fake handler on the named HttpClient `Touchque`.

### Fixed
- **JSON that repeats a member name or holds a lone surrogate.** System.Text.Json parses it and throws `ArgumentException` (a repeated name) or `InvalidOperationException` (a lone surrogate) only when that object or string is first read. Reading one member of an object reads all of its names. So:
  - **JWS verifiers.** They read a token's header before checking its signature, so a header that repeated a member name, or held a lone surrogate where they read it, made them throw that exception instead of their own error (a 500 where a 400 or 401 was due). Claims were read only after the signature check, except a DPoP proof's (checked with the key in the proof itself) and `ApprovalToken.Decode`'s (not checked: it returned header and claims unread, and the caller's first read threw). The SDK now checks that a JWS header and claims are I-JSON (RFC 7493; RFC 7515 section 5.2 allows refusing a repeated header name) before anything reads them:
    - `IdJagVerifier.VerifyAsync`: `TouchqueIdJagException` `invalid_grant` ("assertion is not a JWT"). `RequestIdJagAsync` with a `DpopKey`, which read the returned ID-JAG's claims to set `DpopBound` and threw on them: `DpopBound` false for such an ID-JAG.
    - `HostedLogin.VerifyAccessTokenAsync` and `VerifyIdTokenAsync`: `HostedLoginException` `invalid_token`, so the `TouchqueBearer` handler answers 401 instead of throwing out of `UseAuthentication`.
    - `McpAuth.VerifyAsync`: 401 `invalid_token` for the token, `invalid_dpop_proof` for its DPoP proof.
    - `SecurityEventVerifier.VerifyAsync`: `TouchqueSecurityEventException` `invalid_request`. `ApprovalToken.Decode` and `VerifyWith`: `TouchqueApprovalMismatchException`.
  - **`AgentCard.VerifyAsync`** read the whole card (its RFC 8785 canonical form) and threw on a card that repeated a member name anywhere or held a lone surrogate: such a card is now `malformed` (from `AgentCard.Sign` too), and a signature whose protected header does is skipped.
  - **Token endpoint answers.** `RequestIdJagAsync` and `RedeemIdJagAsync` threw on an error answer whose JSON repeated a top-level member name or held a lone surrogate in `error` or `error_description` (they read those), and `RequestIdJagAsync` on a 2xx answer that did so in a field it reads; `RedeemIdJagAsync` returned a 2xx answer like that for the caller's first read to throw. Now a 2xx answer that repeats a member name or holds a lone surrogate anywhere throws `TouchqueIdJagException` `invalid_response`, and the body of such an error answer is not read, so its `Error` is `server_error`. An error answer whose JSON `error` was empty gave `Error` ""; it is now `server_error`.
  - **Webhooks.** `WebhookResource.Verify` and `VerifyAsync` threw `ArgumentException` on a body that repeated a top-level member name, when they read the payload: at once when the signature came from the body rather than `x-signature`, else after the signature check, which a Touchque delivery with one of its members repeated passes (the canonical form keeps the last). A body `signature`, or a top-level member name, with a lone surrogate threw `InvalidOperationException`. `MapTouchqueWebhook` answered 500 to these. Now a body that repeats a member name at any depth, or has a lone surrogate in a member name, is refused with `TouchqueWebhookSignatureException` "invalid JSON payload", and such a body `signature` with "invalid signature" (`MapTouchqueWebhook`: 401). A lone surrogate in another value is still accepted: Touchque's JSON.stringify writes one, escaped, when a string it sends holds it.
- **Token endpoint answers with a charset .NET does not know.** `RequestIdJagAsync` and `RedeemIdJagAsync` threw `InvalidOperationException` for an answer whose `Content-Type` named one, such as `application/json; charset=utf8`. JSON is UTF-8 (RFC 8259), so the answer is now read as UTF-8 whatever its charset, a leading byte order mark skipped.

## [5.2.0] — 2026-11-13

The first release on NuGet since 4.2.0, as `Touchque` and `Touchque.AspNetCore`. NuGet package IDs are case-insensitive, so these are the same packages as 4.2.0's `TouchQue` IDs: from 5.2.0 on, nuget.org shows the new spelling, and 4.2.0 keeps the old one. 5.0.0 and 5.1.0 were not pushed to NuGet; their changes ship in this release.


### Added
- **`Guard.RunAsync(null, input)`: the default client.** A null client is `Guard.DefaultClient()`, built from `TQ_API_KEY`, `TQ_API_SECRET` and `TQ_API_URL` on the first request and kept; a build that fails is not kept, so the next request tries again. It is thread-safe. While it cannot be built, the guard answers 401 `unauthenticated` without a user, else 500 `misconfigured`, and never throws; nothing is logged then, since the SDK's logger belongs to a client. `Guard.IsStatusPoll(null, input)` uses the same client and is false while there is none. It reads the environment only, not `AddTouchque`'s options (see the README for resolving that client per request).
  - `Guard.SetDefaultClient(client)` replaces it process-wide, for example with a client built with a `Logger`, which gives the null-client path its log lines; null forgets it, so the next call builds one from the environment again.
  - To fail fast at startup, call `Guard.DefaultClient()`: it throws `TouchqueConfigException`, naming the problem.
- **ASP.NET Core: `r.ToResult(errorBody)` and `await r.WriteAsync(http, errorBody)`: a guard result as its HTTP answer** (`TouchqueGuardResultExtensions`, extension methods on `GuardResult`). For a step or a refusal (an approval throws `ArgumentException`): `Cache-Control: no-store`, `Retry-After` on 423 and 429, `X-Touchque-State` and `X-Touchque-Reason` on a refusal, and the JSON body. `errorBody` follows the `ErrorBody` rules: refusals only (400 or more), written with the app's JSON options (MVC's in a controller action, else the minimal APIs'), an object gets `touchque` set to the step, anything else is sent as it is, a callback that throws or a result that cannot be written sends the default body and logs through `TouchqueOptions.Logger`.
  - `RequireTouchque`, `[RequireTouchque]` and `MapTouchqueRelay` build their answers with the same code, so a guard inside your handler answers exactly like them.
- **Waiting polls carry `expiresAt`.** A `waiting` or `passkey_required` step with `expiresAt` puts it in its token as the claim `rx` (ms since the epoch), and every later poll answer for that request in those states carries `expiresAt`, also after a detour through the offline QR. Before, only the first answer had it, so a page reading the latest answer never stopped by time. A poll takes the live expiry from the status answer when it parses (a Vishing Shield escalation to a passkey extends the request to 180 s), else `rx`, and the re-issued token keeps the one used. With neither, no `expiresAt`, as before.
- `GuardTokenClaims.RequestExpiresAt` (`rx`, Unix milliseconds): `GuardToken.Sign` writes it and `GuardToken.Verify` reads it, so a token you verify and sign again keeps `expiresAt` on its polls.
- `LoginStatus.ExpiresAt`: the request's live expiry from `GET /login/status` (null when the API did not say, or sent something other than a string, so a poll falls back to `rx`). The step of `CheckAsync(requestId)` carries it.

### Changed
- **`Enroll = false` says why.** A user with no phone on a guard that may not show a first-time QR (`GuardInput.Enroll`, `TouchqueGuardOptions.Enroll`, `StartOptions.Enroll`, the relay's `/login` without `GetLoginUser`) gets 202 `{"touchque":{"state":"enroll","reason":"enrollment_off"},…}` instead of a bare `enroll` step. `@touchque/web` 2.2.0 stops polling there and shows that no phone is linked yet.
- `GuardRefusal.From(result)` takes the step from `result.Step` when the body has no `touchque` (a `BeforeStart` hook's result).
- An API answer that does not fit its type throws `TouchqueNetworkException` ("could not read the answer: …"), as in the Java SDK, instead of `JsonException`, so a guard answers 503 `unavailable` instead of throwing.
- README, "Guard inside your handler": the client is resolved per request from `HttpContext.RequestServices`, with `Guard.WithoutClient(input)` while it cannot be built (a `TouchqueClient` handler parameter is resolved from DI before your code runs and throws without keys); `Guard.RunAsync(null, …)` for keys in the environment only, which logs nothing (fail fast with `Guard.DefaultClient()` at startup, or give it a logger with `Guard.SetDefaultClient`); the answer from `r.ToResult()`. Also: a new first-time QR comes about 15 s before the old one expires, with new recovery codes, and the old QR and codes stop working; waiting polls carry `expiresAt`; `Enroll = false` answers `enrollment_off`; a 202 state other than `waiting` or `enroll` needs `@touchque/web` or your own UI following the contract. The snippets are compiled with the tests.

## [5.1.0] — not published on NuGet (these changes ship in 5.2.0)

### Added
- **ASP.NET Core: `ErrorBody` keeps your app's error shape.** `TouchqueGuardOptions.ErrorBody` (`Func<GuardRefusal, object?>`, on an endpoint's `RequireTouchque`, or on `[RequireTouchque]` through `Configure` / `ConfigureAll<TouchqueGuardOptions>`) receives every refusal with status 400 or more (401, 403, 408, 423, 429, 500, 503) as a `GuardRefusal`: `Status`, `Code` (`error.code`, else the step's `reason`, else its `state`), `Message` (`error.message`, else a sentence for the state) and `Touchque` (the step). It is never called for a 202 step or on approval.
  - What it returns is written with the app's JSON options: MVC's for `[RequireTouchque]`, the minimal APIs' for an endpoint. When that gives a JSON object (anonymous, a record, a dictionary, a `JsonObject`), it is sent with `touchque` set to the step and no other spelling of that key (keys keep their case), so `@touchque/web` still sees the state. No `token` is added.
  - Anything else (a string, a number, an array, null) is sent as it is. The status and headers stay the same (`Cache-Control: no-store`, `Retry-After`, `X-Touchque-State`, `X-Touchque-Reason`). The callback gets a copy of the step.
  - A callback that throws, or a result the serializer cannot write, logs `[Touchque] errorBody failed: <message>`, and the default body is sent.
- **Refusal headers.** Every guard answer with status 400 or more, from `RequireTouchque` / `[RequireTouchque]` and from `MapTouchqueRelay`, carries `X-Touchque-State: <state>`, and `X-Touchque-Reason: <reason>` when the step has one. `@touchque/web` 2.1.0 reads the step from them when a body has no `touchque` (an ErrorBody's string, say). A page on another origin must expose them (`Access-Control-Expose-Headers`). `GuardResult.RefusalHeaders`, `Guard.StateHeader` and `Guard.ReasonHeader` give them to a guard of your own.
- `GuardInput.BeforeStart`: see the first-time linking fix below.
- `GuardRefusal.From(result)` and `Guard.WithoutClient(input)` (401 without a user, else 500 `misconfigured`), for guards of your own. `GuardTokenClaims.EnrollExpiresAt` (`ee`) and `ResetSecretResult.TtlMs`.
- README: "Guard inside your handler" (`Guard.RunAsync` after your own checks, how to answer, running the action once, the 202 and first-time QR polls), the `ErrorBody` option and what a missing key answers. The snippets are compiled with the tests.

### Fixed
- **First-time linking: one QR per enrollment, not one per poll.** In 5.0.0 every poll with an `enroll` token started again (login request, 404 `device_not_linked`, generate-secret 409, reset). Each 1.5 s poll replaced the QR and the recovery codes on screen, so the QR being scanned stopped working. Now:
  - An `enroll` step with a QR carries `Enroll.ExpiresAt`: the API's `expiresAt` when it is ISO 8601, else now + `ttlMs`, else none. Its token carries that expiry as the claim `ee`.
  - A poll with that token only reads the link state (`Auth.GetUserAsync`). Not linked and the QR good for more than 15 s: 202 `{"touchque":{"state":"enroll","expiresAt":…},"token":…}` without `enroll`, and the page keeps its QR. Linked: the push starts. Expired or about to, or the user unknown (404): a new QR. Other errors answer 503 `unavailable`.
  - `Guard.IsStatusPoll` is true for such a poll while the QR has more than 15 s left, so the relay's per-user limit no longer refuses enrollment polls.
  - Every start is charged. `GuardInput.BeforeStart` (`Func<Task<GuardResult?>>`) is called once, right before such a poll starts anything (a silent check or a push once the phone is linked, a new QR once the old one expired, is about to, or is gone), and a result it returns is answered instead. The relay's `POST /login` charges that start on the user's `login` limit like a fresh attempt and answers its usual 429 when it is over. So polls that only keep the QR are free, and replaying a first-time token can neither start pushes nor renew the secret on the poll budget.
  - A 5.0 token (no `ee`) works as before. Pages on `@touchque/web` need 2.1.0.
- **ASP.NET Core: a missing API key no longer throws on a guarded request.** `AddTouchque()` already built the client on first use, so the app started, but a `RequireTouchque` endpoint then threw `TouchqueConfigException`. Now, while the client cannot be built (no `TQ_API_KEY` / `TQ_API_SECRET`), the endpoint never runs: it answers 500 `misconfigured` (401 `unauthenticated` without a signed-in user) with `Cache-Control: no-store`. The SDK logs once through `TouchqueOptions.Logger` (or `Debug`): `[Touchque] TQ_API_KEY and TQ_API_SECRET are not set: routes guarded by Touchque answer 500 misconfigured.` `MapTouchqueRelay` still needs the keys at startup.

## [4.2.0] — 2026-11-10

### Changed
- **NuGet package IDs are `Touchque` and `Touchque.AspNetCore`**, the brand's spelling. The namespaces and assembly names did not change in this release (5.0.0 renames them), so code does not change (NuGet IDs are case-insensitive).

### Security
- **The offline approval-token check refuses another workspace's token.** `GET /agents/jwks.json` is one key set for every Touchque workspace, and the check used to compare `aud` only when you passed an audience, so a token Touchque signed for someone else's workspace (their own phone, any person's name, any details) could pass your executor. Now:
  - `Agents.VerifyApprovalTokenAsync(token, audience = null, expect)` uses this workspace's own audience by default: `Agents.ApprovalAudienceAsync()` asks `GET /agents/approval-audience` once (`touchque:workspace:<id>`) and keeps it.
  - `ApprovalToken.VerifyWith(token, jwks, audience, ...)` requires the audience. A missing or empty one throws TouchqueApprovalMismatchException (`audience is required`).
  - A token without `aud` is refused (`the approval token names no workspace`), as is one for another workspace (`the approval token is for another workspace`).
  - Breaking for callers of the low-level function who passed no audience: pass Agents.ApprovalAudienceAsync()'s value.
  - `redeemApproval` was already safe: Touchque compares `aud` with your workspace there.

### Added
- **`DeviceRisk.SearchEventsAsync(new DeviceRiskSearchOptions { ... })`: search your workspace's Device risk identifications**, newest first, one page at a time (`GET /device-risk/events`): `From`/`To` (7 days by default, at most 90, within your retention), `Signal`, `StepUp`, `Kind`, `Origin`, `Ip` (an address or a CIDR range; never returned), `Account`, `VisitorId`, `RequestId`, `Limit` (1 to 100) and the opaque `Cursor` from the previous page's `NextCursor`. `DeviceRiskSearchResult` record.
- `DeviceRiskCheckResult.Engine` (`string?`): the engine's state for this check; `unavailable` when the risk engine could not be reached and the verdict is a safe default (`StepUp` true), so an outage can be told apart from risk.
- **`WebAuthn.PrimaryAvailabilityAsync()`: is passkey sign-in on for your workspace?** `GET /webauthn/authenticate/primary/availability` answers a `WebAuthnPrimaryAvailability` (`Enabled`, `UserVerification` `required` or `preferred`, null when off). Ask before your sign-in page shows its passkey button and passkey autofill; when it is off, `PrimaryOptionsAsync` answers 403 `passwordless_login_disabled`.
- **Shared Signals: receive the security events an identity provider sends after sign-in.** Touchque SSO sends Security Event Tokens (OpenID Shared Signals Framework 1.0) for an organization's members to the receivers its admin adds (Organization > Continuous access): CAEP `session-revoked`, `credential-change`, `device-compliance-change`, RISC `account-disabled`, `credential-compromise`; `txn` carries the case code of Touchque's decision. `new SecurityEventVerifier(new() { Issuer, Audience, JwksUri?, Jwks?, ClockSkew? }).VerifyAsync(token)` returns a `SecurityEvent` (`Jti`, `Issuer`, `Audience`, `IssuedAt`, `Txn`, `Subject`, `Type`, `Name`, `Claims`) or throws `TouchqueSecurityEventException` with the RFC 8935 code to answer in `Error` (`invalid_request`, `invalid_key`, `invalid_issuer`, `invalid_audience`); `SecurityEvents.PollAsync(new() { Url, Token, Ack, SetErrs, MaxEvents })` for poll delivery (RFC 8936); `SecurityEvents.Types`. The keys come from the issuer's `/.well-known/ssf-configuration`; a SET does not expire, so keep the jtis you handled. Tested against the shared vectors (`fixtures/security-event-vectors.json`).
- **Safe Guard: Safe transactions approved on the approver's phone, for TouchqueSafeGuard.** `tq.SafeGuard.RequestAsync(new SafeGuardRequestOptions { ExternalUsername, Type, SafeTx })` sends the raw transaction (the phone decodes it itself and signs with a key only its biometrics unlock), `StatusAsync(requestId)` and `WaitForApprovalAsync(requestId)` hand back the 105-byte approval. `SafeApproval.Verify(target, approval, approverKey, new VerifySafeApprovalOptions { Purpose, ApproverIndex, Rows | DisplayDigest, Now })` checks it the way the guard does, without trusting Touchque: the Safe transaction hash (EIP-712, Keccak-256 here) and the governance hash computed here, the 149-byte message, low `s`, the one-day expiry window, the P-256 signature. `SafeApproval.WithApprovals(ownerSignatures, approvals)` for `execTransaction`, `SafeApproval.ScheduleCall(safe, governanceHash, approvals)` for a governance change; `SafeTxHash`, `GovernanceHash`, `Message`, `DisplayDigest`. Tested against the shared vectors (`fixtures/safe-guard-vectors.json`).
- **Guard tokens with typed claims:** `GuardToken.Sign(apiSecret, claims)` and `GuardToken.Verify(apiSecret, token)` (Node `signGuardToken` / `verifyGuardToken`) sign and check the token `Guard.RunAsync` hands the browser, for a flow of your own. `GuardTokenClaims` names the short claims (`User`, `Action`, `DetailsDigest`, `ReferenceId`, `State`, `RequestId`, `Number`, `OfflineChallengeId`, `CaseCode`, `ExpiresAt` in Unix milliseconds); `Verify` returns null for a missing, changed, foreign, expired or incomplete token. Tokens are byte-for-byte those of the Node SDK.
- **Webhook events of Never Locked Out and the help desk:** `WebhookResource.EventRecoveryStarted`, `EventRecoveryDeviceBound`, `EventRecoveryCooling`, `EventRecoveryCompleted`, `EventRecoveryVetoed`, `EventRecoveryExpired`, `EventRecoveryFailed` (`RECOVERY_*`) and `EventAssistOpened`, `EventAssistEnded`, `EventAssistCheckPassed`, `EventAssistCheckFailed`, `EventAssistUnfrozen`, `EventAssistClaimConfirmed`, `EventAssistClaimUnverified` (`ASSIST_*`).
- Shared Signals: a README section (verifying a pushed SET, polling) and tests for discovery through `/.well-known/ssf-configuration` and for `SecurityEvents.PollAsync` against a transmitter on this machine.

### Fixed
- `Login.VerifyAsync` (and `TouchqueClient.ProtectAsync`) now send `ExpiresIn` and `ClientSignals` with the request; they were dropped, so the push expired after the 30-second default and the page's automation check never reached the risk engine.
- `MapTouchqueRelay` works on a nested route group (`app.MapGroup("/api").MapTouchqueRelay("/touchque")`) and under a prefix with route parameters; every relay call answered 404 there.
- An empty `ReferenceId` counts as no reference in `CompleteAsync`, so an approval started with `ReferenceId = ""` is no longer used up and then refused as a mismatch. `Guard.RunAsync` (the `RequireTouchque` filter and the relay) answers 503 `unavailable` for an approval mismatch instead of letting the exception escape as a 500.

### Security
- **Hosted login: an empty `iss` is refused too (RFC 9207).** `HandleCallbackAsync` (and so `MapTouchqueLogin`'s callback) already refused a callback whose `iss` names another issuer; one with an empty `iss=` now throws `issuer_mismatch` as well, before the code is exchanged. A callback without `iss` (a server that does not send it yet, or a null value) is still accepted.
- `SafeApproval.Verify` without `Purpose` now accepts only an ordinary approval (`approve`). An approval to schedule a governance change covers no Safe nonce or gas fields and is accepted only when you pass `Purpose = "schedule"`; before, either purpose passed and a caller treating `Valid` as permission to execute could be handed a schedule approval.
- `HostedLogin` and `MyAccount` refuse a plaintext `http://` Domain except on localhost (`localhost`, `127.0.0.1`, `::1`, `*.localhost`), as `TouchqueOptions.BaseUrl` does; authorization codes, PKCE verifiers, the client secret and tokens would otherwise travel in the clear.
